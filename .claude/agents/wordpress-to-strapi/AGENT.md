# WordPress -> Strapi/Next Orchestrator Agent

WordPress-specialized orchestration flow in strict order:

`W -> B -> D -> E -> Final Data Migration` (with mode-based skips)

with mandatory human checkpoints.

## Arguments

- `$ARGUMENTS[0]`: WordPress URL (required)
- Optional flags:
  - `--cms-only`: run only Phase W
  - `--skip-tests`: skip Phase B and continue with D -> E
  - `--import`: trigger import path in WP scripts when applicable

If missing, stop and ask exactly:

`/wordpress-to-strapi <wordpress-url> [--cms-only] [--skip-tests] [--import]`

## Contract (hard rules)

1. Never skip WP-1/WP-2 checkpoints.
2. Never run downstream phases before required approvals.
3. Never weaken parity tests to force pass.
4. Frontend must be CMS-backed and dynamic (no static primary content).
5. Keep all artifacts under `output/<site>/`.
6. Initial entrypoint is command-only: `/wordpress-to-strapi ...` (do not treat agent/script as user entrypoint).
7. Separate common engine vs project-specific runner strictly:
   - common engine: `scripts/wp-migration/*`
   - project-specific generated runtime: `output/<site>/wp-migration/*`
8. Schema/CMS creation happens before frontend phases; full data migration runs last via generated project-specific runner.

## Runtime modes

| Mode        | Trigger                      | Execution path |
| ----------- | ---------------------------- | -------------- |
| Default E2E | `/wordpress-to-strapi <url>` | W -> B -> D -> E -> Final Data Migration |
| CMS only    | add `--cms-only`             | W -> Final Data Migration |
| Skip tests  | add `--skip-tests`           | W -> D -> E -> Final Data Migration |

## Detailed Execution Steps (canonical order)

1. **Start from command only**  
   Run `/wordpress-to-strapi <wordpress-url>` to initialize the project and derive `site-slug`.

2. **Create CMS foundation (Strapi project/bootstrap)**  
   Create/configure CMS runtime and roles/permissions for the target project.

3. **Generate schema from WordPress structure (AI + deterministic analysis)**  
   Use extracted/normalized/detected WordPress structure to infer content model and generate Strapi schema.

4. **Apply schema to CMS + validate GraphQL/types**  
   Apply generated schema to Strapi, restart CMS, and validate GraphQL/types/contracts.

5. **Migrate sample-level data for testing (preview stage)**  
   Import preview/sample content so testing and frontend generation can proceed safely before full data migration.

6. **Run frontend flow (Phase D)**  
   Generate Next.js frontend from CMS adapter contracts and enforce dynamic CMS data usage.

7. **Run quality flow (Phase E)**  
   Execute parity + Sonar + Lighthouse + remediation loop to stabilize the generated stack.

8. **Generate and run full DB/data migration script at the end**  
   Use generated project-specific script from output folder:
   - `cd output/<site>/wp-migration`
   - `node run-full-migration.mjs`
   Then report import counts/parity at `WP-2`.

9. **Return final handoff command to user (mandatory)**  
   Always print the exact command for full data migration:
   - `cd output/<site>/wp-migration && node run-full-migration.mjs`

Script entrypoints:

- `scripts/wp-migration/wordpress-to-strapi.mjs`
- `output/<site>/wp-migration/run-full-migration.mjs` (generated by initial WP flow)

Never run generated `run-full-migration.mjs` before schema/CMS setup is complete (`WP-1` approved).
After initial flow, data reruns must use generated script from `output/<site>/wp-migration/` (no WordPress URL re-entry).

## Final Data Migration (project-specific runner)

Run as the last step of the flow.

Skill: `.claude/skills/PA-reverse-engineering/wp-data-migration/SKILL.md`

Commands:

```bash
cd output/<site>/wp-migration
node run-full-migration.mjs             # default: extract + upsert + verify
node run-full-migration.mjs --extract-only
node run-full-migration.mjs --verify
node run-retry-failed.mjs
```

Rules:

- **Default run writes to Strapi** (upsert). Use `--extract-only` to skip import.
- Engine code lives in `scripts/wp-migration/lib/*`; this directory holds site config, data, and logs.
- Do not ask for WordPress URL again.
- Upsert by `wpId`; media skips when already in `full/sync/id-map.json`.
- Logs: `full/sync/migration-run.log` (text), `full/sync/import-log.json` (JSON).
- Failures: `full/sync/failed-imports.json` (`source` + `payload`) → `node run-retry-failed.mjs`.
- Exit code `0`; `verification.passed` true; `failed-imports.json` count `0`.
- Env from shell or `frontend/.env.local`.

### CHECKPOINT WP-2

After full data import, present import counts, verification summary, and `import-log.json` errors (if any); wait for explicit approval.

## Failure Handling

| Failure | Action |
| --- | --- |
| WP API blocked/auth failed | Stop and report; request export credentials or alternate source |
| Unknown-structure AI validation fails | Retry with constrained mapping; escalate after cap |
| Full import exits 1 or verification failed | Read `full/sync/failed-imports.json` + `migration-run.log`; fix; `node run-retry-failed.mjs` |
| User used `--extract-only` but expected Strapi data | Re-run without `--extract-only` |
| Final data import parity mismatch | Block WP-2 until reconciled |
| Route/parity mismatch in D/E | Return to Phase D mapping; rerun validations |
| Quality gate unresolved after remediation cap | Produce failure report and escalate |

## Relation to URL Flow

- `url-to-strapi` remains the generic source orchestrator (`A -> E`).
- `wordpress-to-strapi` is WordPress-specialized hybrid orchestration (`W -> B -> D -> E -> Final Data Migration`).
- Both share downstream quality expectations and immutable checkpoint behavior.
